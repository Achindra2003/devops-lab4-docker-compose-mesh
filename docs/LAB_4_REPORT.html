1. Project Description & Problem Context

Modern cloud-native platforms rely on multi-container orchestration where independent services coordinate across network and storage boundaries. The prompt for this laboratory is to develop and deploy a multi-container application using Docker Compose or Podman, and validate networking and storage.

To eliminate naive anti-patterns (such as flat unsegmented bridge networks and ephemeral database storage), we engineered MeshPulse: a four-tier distributed microservice stack comprising an Nginx edge gateway, a multi-stage Node.js core API, an append-only Redis cache, and an automated network sentinel.

3. Network Segmentation & Zero-Trust Validation

We designed dual isolated bridge networks to enforce least-privilege traffic flow:

  • frontend-net (172.28.1.0/24): Connects Edge Gateway and Core API for public HTTP ingress.
  • backend-net (172.28.2.0/24): Connects Core API, Redis Cache, and Sentinel Watchdog for private data operations.

4. Storage Tier Validation & Data Durability

We implemented a Tri-Tier storage hierarchy validating persistence and security boundaries:

Storage Tier Mount Type Target Path Operational Role
Tier 1 Named Persistent Volume redis_data:/data Append-Only File (AOF) durable storage surviving container destruction.
Tier 2 Read-Only Bind Mount ./nginx/nginx.conf:ro Host configuration injection with write-protection against tampering.
Tier 3 In-Memory Tmpfs Mount /tmp (64MB) High-speed RAM-backed ephemeral storage with zero physical disk I/O.

5. The Seven Self-Learning Initiatives

  1. Multi-Tier Zero-Trust Network Segmentation: Dual bridge networks preventing direct database exposure from edge ingress.
  2. Tri-Tier Storage Strategy: Orchestrating Named Volumes, Read-Only Bind Mounts, and Tmpfs RAM mounts simultaneously.
  3. Automated Disaster Recovery Testing: Scripted verification proving zero data loss across container lifecycle destruction.
  4. DNS Service Discovery Architecture: Fully automated service discovery via Docker embedded DNS without hardcoded IPs.
  5. Healthcheck-Driven Dependency Orchestration: Eliminating race conditions using condition: service_healthy.
  6. Least-Privilege Non-Root Hardening: Microservice execution as UID 1000 with no-new-privileges:true.
  7. Automated CI/CD Validation Pipeline: GitHub Actions pipeline verifying unit tests, compose startup, network isolation, and storage recovery.

6. Key Learnings & Engineering Reflections

1. Network Segmentation is Essential: Single flat bridge networks expose internal databases to edge breaches. Dual-homed bridge networks provide defense-in-depth.

2. Storage Must Match Lifecycle: State belongs in named persistent volumes with AOF; configs belong in read-only bind mounts; ephemeral tokens belong in tmpfs RAM.

3. Dependency Ordering Requires Probes: Standard Compose depends_on is insufficient because it only checks container creation, not runtime readiness.
